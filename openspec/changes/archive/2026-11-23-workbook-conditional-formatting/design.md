## Context

ECMA-376 Part 1, 18.3.1.18 and 18.3.1.10, define `x:conditionalFormatting` and `x:cfRule`. A rule names a differential format (`x:dxf`, 18.8.14) in the style part by `@dxfId`. The first change keeps every rule through a save and refuses structural edits on a sheet that holds one (`store/structure/blockers.ts`). The fixture `preserved-parts` has one rule over B1, `cellIs` `greaterThan` 3, whose differential format sets bold. Its reference PDF draws the value 5 in `Calibri-Bold`.

## Goals and non-goals

The goal is to paint the rules that the engine can decide from the stored values alone, and to paint nothing for the others. A rule that is not shown has an unknown result, so a lower shown rule can paint where the file, with every rule known, paints something else (D4). Formula evaluation stays out of scope, as `AGENTS.md` states.

## Decisions

### D1. Lanes

`cascade/conditional.ts` reads and evaluates the rules, and `cascade/cell-format.ts` lays a differential format over a cell format. Layout calls the overlay for each resolved cell. The lane graph does not change: `cascade` reads `store`.

### D2. Rule reader and limits

- The reader takes the `x:cfRule` children of each `x:conditionalFormatting` in document order, and caches the result per worksheet root.
- `@priority` is an `xsd:int`, and any XML white space separates the ranges of `@sqref` (`ST_Sqref` is a list).
- Limits: 4,096 rules for each sheet, 65,536 rule and range pairs for each sheet, 512 ranges and 16,384 characters for each `@sqref`, and 8,192 characters of an operand. A rule past the sheet limits is counted as skipped and never built. A rule past the `@sqref` limits is `malformed`, and an operand past its limit is `needs-formula`. A range is four numbers: the reader never allocates for the cells that it names.
- A rule without `@priority`, with an unreadable `@dxfId` or `@sqref`, with no operator, or with the wrong count of `x:formula` children is `malformed`. A range of `@sqref` is read as an uppercase cell reference or cell range without `$` (`A1` or `A1:B2`). A whole-column range (`A:A`), a whole-row range (`1:1`), a `$` mark, and a lowercase column letter are valid `ST_Sqref` text, but the engine cannot read them, so such a rule is also `malformed`, and the notice of D4 shows. The operands are read in order, so a rule whose first operand needs a formula is `needs-formula`, whatever the count. Either reason keeps the rule from being shown.

### D3. What the engine evaluates

- A rule is shown when it is `cellIs` and each operand is a literal: a number in the `xsd:double` form, a quoted string with doubled quotes, `TRUE`, or `FALSE`, without case.
- Other rule types are `unsupported`, and so is a `cellIs` rule with a text operator of `ST_ConditionalFormattingOperator` (`containsText`, `notContains`, `beginsWith`, `endsWith`). The reader matches elements in the SpreadsheetML namespace only. A `cellIs` operand that is not a literal is `needs-formula`.
- A rule reads the stored value of its cell, also when that value is a cached formula result. When the first change marks that value out of date, the format of the rule follows the same cached value, and the fill or font that the rule adds has no mark of its own. A formula cell without a cached value is not evaluated, because no value exists to test. Layout also evaluates each visible cell without an `x:c` element that a rule covers, and the top-left cell of an empty merged range, with an empty value, and paints its fill and borders in one record with its row or column format.
- Strings compare by UTF-16 code unit after lowercase. Numbers compare without rounding. `between` and `notBetween` include their bounds.
- The reasons of rules that are not shown have no consumer in the editor. The notice of D4 reads only whether a sheet has such a rule or skipped rules.
- Comparison: numbers order before strings, and strings before booleans. Strings compare without case. An empty value is 0 against a number and the empty string against a string (measured on B16 to B18). An error value, an ISO date value (`t="d"`), and an empty value against a boolean make the rule false. `between` and `notBetween` accept the bounds in either order.

### D4. Priority and the overlay

- The walk takes the rules over a cell by ascending `@priority`, then document order. Each property takes the first value that a true rule sets. A true rule with `stopIfTrue` ends the walk. A rule that is not shown is skipped: it never paints and never ends the walk. This includes rules past the sheet limits and rules in `x:extLst`. So a lower shown rule can paint a property that a true rule above it, which the engine does not show, would set first or would stop. The approximation names this case; ending the walk at such a rule would instead hide lower rules that the file shows, and neither choice has a measurement.
- Cost: the ranges of the shown rules that meet a row are built once for each row, in one pass over the rule and range pairs, and cached for each sheet. A row keeps at most 1,024 ranges, and the cache of a sheet keeps at most 4,096 rows and 262,144 ranges. For one cell, at most those 1,024 ranges of its row are checked, and at most 64 shown rules are walked. A rule with two ranges over the cell is walked once. A cell outside the columns of every range of its row checks no range. One layout stops checking when it has used 4,000,000 rule-range checks, counting each row that it builds as all the pairs of the shown rules, and each string comparison as one check for each full 16 code units of the shorter string; the row or cell that crosses the limit finishes first. Past that budget, the remaining cells keep their cell formats, layout sets `conditionalCut` and records the problem `conditional-budget`, and the editor shows the notice of this decision.
- The overlay sets the font properties that the differential `x:font` sets, including the family and size. A solid or untyped `x:patternFill` paints its `x:bgColor`. Without `x:bgColor`, it keeps the fill of the cell format, and paints white over a cell with no fill (measured on B10, B23, and B24). Any other differential fill keeps the fill of the cell format: `patternType="none"`, another pattern type, and `x:gradientFill`. An `x:numFmt` replaces the number format. Borders, alignment, and protection do not apply.
- The overlay does not change row heights: the auto height of a row reads the cell formats only.
- The plain text of a copy and the announcement of the active cell apply the differential number format of a true rule, as the grid does. After a budget cut of the shown sheet, the grid can show the cell format where a rule is true, so both use the cell format, as the hint does. A copy shares one check budget of 4,000,000 over its cells, as one layout does, but it charges each row once in full, also a row in the cache, and each cell for its own checks, so the result depends only on the range and not on what was laid out or copied before. A copy or a cut that runs out of it is refused with `copy-conditional-limit`: a refusal shows in the status strip and returns a code, so the copy is never silent and never mixes the two forms. The copy does not change the grid, so it does not mark the cut: the notice, the hint, the announcement, and later copies keep the rules. Through the internal payload, a paste writes the cell format, never the rule; the plain text that another program pastes carries the shown text.
- The toolbar state and the cell editor read the cell format without the overlay, because a format command changes the cell format. The grid can show a rule's bold, fill, color, or number format while the matching command shows the cell format, so the command has no visible effect on that cell. So the snapshot holds `conditionalFormat`, the format state that the grid shows at the active cell when a true rule changes it, and `toolbarCommandState` gives the hint `hint.conditionalFormat` to each format control whose state differs there. The chrome shows the hint after the label in the tooltip, and as the accessible description. Rich text runs are not read, as the toolbar state does not read them. The cell editor shows the cell format while it is open, with no hint. The hint marks a control whose state differs. When the cell format and a true rule give the same state, the control shows that state with no hint. A press then changes the cell format, the states differ, and the hint shows at once on the pressed control. The hint follows the disabled reasons of this engine: the engine names a catalog key, and the adapter translates it. DOCX Editor differs at `f3116761`: its engine states a disabled reason in English, and its catalog maps the sentence to a key (`packages/i18n/src/disabled-reasons.ts`). DOCX Editor has no hint for state that a style sets, so the hint is a difference from DOCX Editor, recorded here.
- A rule that is not shown is never silent. The snapshot states `conditionalHidden` when the shown sheet has a rule that is not shown, rules past the read limits, more than 64 shown rules or 1,024 shown ranges (the caps of one cell and one row can then take effect), or `x14:conditionalFormattings` in `x:extLst`, and when a layout of the shown sheet ran out of its budget. A notice from the budget stays with its sheet part, not with the sheet index, so a sheet move keeps it and a sheet delete does not pass it to the sheet at the same index. It stays until the shown sheet changes or another workbook opens, so the size of the window cannot turn it on and off; after a cut, no control gets the hint. The row cache outlives one layout, and a cached row costs nothing, so a window can cut in one layout and not in a later one; the notice stays in that case. The chrome then shows the notice `status.conditionalHidden` through the notice channel of the stale-results notice.

### D5. Evidence

- The reference PDF of `preserved-parts` measures one `greaterThan` rule that sets bold.
- The fixture `conditional-rules` (`scripts/fixtures/conditional-cases.ts`) measures the eight operators, `between` in both bound orders, true and false `notEqual`, number and string operands, text values under number and string operands, a boolean value under a string operand, an error value, empty cells with and without `x:c`, a fill from `x:bgColor` under `solid` and no `patternType`, theme colors with tint, a rule fill over a cell fill, a font color, italic, the presence of strike and underline (layout draws them up to 1 point off the reference, as the approximation states), a number format, two true rules that set different properties, `stopIfTrue`, and a fill with only `x:fgColor` over a cell with and without its own fill. Its reference PDF agrees with D3 and D4 in each case, and both its saved and edited copies pass the save check.
- The reference PDF draws a right-aligned italic or bold-italic number 2 points left of a regular one. Layout does not. The cause has no measurement: no reference PDF has italic text from a cell format, so only italic from a differential format is measured. The harness records it as a known line position gap of 2 points, with its cause in the approximation "Measured text offsets".
- The pixel score cannot tell a bold glyph from a regular one, so layout tests check the face, the decoration, the color, and the fill of each cell of column B of `conditional-rules`, and the face of B1 of `preserved-parts`, and keep the italic numbers at the x of the regular ones.
- The approximation "Conditional formatting rules" names the cases without a measurement.

## Risks

- A file with many rules over one cell shows only the first 64 shown rules by priority, and a row with many rule ranges checks only the first 1,024 for one cell.
