title: 'Known approximations'
description: 'Each place where the XLSX Editor render can differ from the reference PDF, and each case that no fidelity check measures.'
category: 'Reference'
---

XLSX Editor measures its rendering against reference PDFs. This page lists each place where the engine knows that its result can differ from the reference, and why. A test (`packages/core/src/layout/__tests__/approximations.test.ts`) keeps the list of known approximations equal to the list in `packages/core/src/layout/approximations.ts`.

An approximation is not a gap. A coverage gap is a case that no check measures. A known gap is a check that a fixture does not pass.

## Known approximations

- **Pixel density.** The column width formulas of ECMA-376 Part 1, 18.3.1.13, round to whole pixels, and the standard does not state a pixel density. The engine uses 72 pixels for each inch: at that density, the reference PDF of `grid-structure` prints each column at the width that the formulas give. A grid that rounds at another density gets other column widths and row heights.
- **Screen geometry.** The screen profile (`SCREEN_PROFILE`) lays out rows without `x:row/@ht` at the line height of their font plus 2 pixels, 15 points for Carlito 11, and does not scale row heights. No committed reference shows them: the reference PDFs show only the printed page, which the print profile (`PRINT_PROFILE`) follows. The rules that the print profile measures in pixels also apply to the pixels of the screen profile without a measurement: the whole-pixel snap of rotated text in the screen profile, and the minimum descent of bottom-aligned text in the screen profile.
- **Tint rounding.** A color with `tint` changes its lightness in the HLS color space, as ECMA-376 Part 1, 18.8.19, states. The engine computes the formula in floating point. On the measured fixtures, `colors-fonts` and `conditional-rules`, each color channel differs from the reference result by at most 2 on a scale of 0 to 255.
- **Row auto height.** A row without `x:row/@ht` (`CT_Row`, ECMA-376 Part 1, 18.3.1.73) takes the tallest row height of the fonts of its cells and their rich text runs, and never less than the default row height. A cell that wraps its text adds the row height of its font for each line that its text breaks into at the width of its column. The reference PDF of `text-layout` measures a Carlito 20 row, a Carlito 8 row, and a row with a 14 point run. The height of a row with wrapped text has no measurement, and a cell inside a merged range does not change the height of its row. Line heights round to whole pixels at each zoom. So a fit of a row with a wrapped cell writes as `@ht` the tallest of these heights at each zoom step from 50% and at the current zoom. It leaves one pixel of each zoom for the rounding, which cuts no line. A row with no wrapped cell takes its height at zoom 1, so at another zoom it can be up to 2 pixels shorter than a row without `@ht`, with no text cut. Lines break at the glyph widths of each zoom, so a wrapped cell can break into one more line at 50% than at 100%. The fitted row then shows an empty line at 100%. At a zoom below 50% that was not current at the fit, a fitted row can be a few points too short, and its last wrapped line can be cut.
- **Row height of very long wrapped text.** Layout measures the first 4,000,000 UTF-16 code units of wrapped text in the rows of a sheet without `@ht`, in row order. Each text run of a cell, also an empty run, adds one more unit to this count. A later wrapped cell takes its line count from its line breaks, its length, and the maximum digit width, so its row can differ from the lines that the cell paints. No reference PDF measures this case.
- **Text layout without a measurement.** The reference PDF of `text-layout` measures alignment (`x:alignment`, `CT_CellAlignment`), indent, wrapping, `justify`, `distributed`, `fill`, `shrinkToFit`, overflow, rotation, stacked text, and numbers that do not fit. The reference PDF of `formula-overflow` shows overflow that stops at a formula with a cached number and at a formula whose cached value is an empty string. The line scores check that stop by the clip edge of each overflowing line (approximation "Line scores of clipped text"). These cases follow the measured rules without a measurement: overflow that reaches a cell with a constant value, because the text of each fixture ends before that cell; overflow that reaches a formula with no cached value, which only a unit test (`packages/core/src/layout/__tests__/sheet-layout.test.ts`) covers; the minimum descent of bottom-aligned text in fonts other than Carlito 6 and 8, which keeps the descent of the default font below a smaller font; and stacked text at the top or center of a cell.
- **Rotated text without a measurement.** The reference PDF of `text-layout` measures rotated text values with `general` alignment at the bottom of a cell, at 45, 90, and -45 degrees, in a cell wide and high enough to hold the line. Layout applies the same rules to these cases without a measurement: angles other than 45, 90, and -45 degrees; -90 degrees (`textRotation` 180), which keeps the text margin above the bottom as 90 degrees does; numbers, booleans, and errors with rotation, which keep the `general` alignment of an unrotated cell; rotated text at the top or center of a cell; an explicit horizontal alignment of rotated text; indent with rotation; rotated text in a merged range; `justify`, `distributed`, and `centerContinuous` with rotation; `wrapText` with rotation, which lays out one line; and rotated text taller than its cell.
- **Measured text offsets.** The reference PDFs measure these cases, and layout differs from them by a fixed amount that a test pins: stacked text sits 1 point right; and a line centered in the merged range of `grid-structure` sits 1 point low, which the fidelity harness records as the `grid-structure` baseline gap of 1 point. In `conditional-rules`, the reference PDF draws a right-aligned italic or bold-italic Carlito 11 number 2 points left of a regular one in the same column, and layout keeps them at one x, which a test checks. The italic comes from differential formats only, so the cause has no measurement; the fidelity harness records this as the `conditional-rules` line position gap of 2 points.
- **Overflow reach.** Text shows across at most 64 empty neighbor cells, so that the layout cost of a window does not depend on the content of distant cells.
- **Drawing objects.** Layout places every anchor (`xdr:twoCellAnchor`, `xdr:oneCellAnchor`, and `xdr:absoluteAnchor`, ECMA-376 Part 1, 20.5), and draws pictures and preset or custom shapes with a solid fill and line. Groups, chart frames, shape text, picture cropping, effects, and gradient or pattern fills are not drawn. A shape style reference takes the color of the reference, not the fill or line style of the theme. A picture paints as a gray placeholder when the engine cannot read its pixel size from its header (any format other than PNG, JPEG, GIF, and BMP), or when browsers do not decode it. The `lighten` and `darken` path fill modes paint the fill under a white or black overlay.
- **Border line styles.** Paint draws each `ST_BorderStyle` (ECMA-376 Part 1, 18.18.3) on the gridline pixels of its cell edge. Only `thin` is measured, on the `colors-fonts` reference PDF. The other styles take the line weights and dash lengths that their names state: `medium` is 2 pixels, `thick` and `double` are 3, and the dashed styles repeat dashes of 1 to 11 pixels.
- **Fill pixels.** The reference PDF of `fills-patterns` measures the pattern tiles (`x:patternFill/@patternType`, `ST_PatternType`, ECMA-376 Part 1, 18.18.55), the linear gradient axes, and the path gradient positions (`x:gradientFill/@type`, `ST_GradientType`), and paint follows the same rules. These differences remain. A pattern tile pixel is 1 point, and paint rounds its edges to whole device pixels. So pixel widths can differ by one device pixel, and the tile period drifts by less than half a device pixel for each bitmap of up to 8 by 8 tiles. A pattern fill paints as the mix of its two colors, in the share of set pixels, when one tile is smaller than 8 device pixels or larger than 512. For example, a pattern shows as one color below 75 % zoom at one device pixel for each CSS pixel. It also paints the mix when the canvas cannot make or place a pattern. The raster tools draw each 8 point tile boundary of a reference pattern one raster pixel off, so the reference raster shows one mixed pixel row in each tile period, and paint shows none. On screen, each pane rounds its own sheet origin to a whole device pixel, so a pattern can step by one device pixel at the edge between two panes. The grid starts on a whole device pixel, so a pattern can move by up to half a device pixel against a cell edge that lies between device pixels. The reference PDF draws a path gradient as an image of 1 point pixels, and paint draws it smooth. A gradient over a merged range has a measurement only for a linear gradient at 0 degrees. The reference PDF draws each row of such a range as its own image, flipped vertically. The flip changes no pixel only at 0 degrees. At the right and bottom edges of such a range, the reference raster shows part of a pixel past the gridline pixel, and paint shows none. The reference PDFs clip the print area 1 point inside its top and left edges, so a fill in the first printed row or column loses that point; paint fills it. At a device pixel ratio that is not a whole number, the browser can resample the canvas, so pattern pixel edges can blur on screen.
- **Gridline color.** On screen, gridlines paint in a light gray when the sheet view names no color. The reference PDFs print no gridlines, so the color has no measurement.
- **Glyph positions.** Paint draws each character of a span at the position that layout measured. A character that layout gives no advance, such as a combining mark, also gets its own position, so a combining sequence can draw apart from its base character.
- **Substitute font outlines.** When the host passes no fonts, the editor and the fidelity harness draw text with the metric-compatible substitutes of `@docx-editor.dev/fonts`, whatever fonts the machine has. A substitute keeps the advances of the family that it replaces, such as Carlito for Calibri, and draws other glyph outlines. The fixtures name the substitutes themselves (Carlito and Liberation Sans), and their reference PDFs embed the same faces, so no fixture measures the outline difference.
- **Glyph rasterization.** The editor draws text as canvas text in the browser. The fidelity harness compares that page with a Poppler raster of the reference PDF, and the two rasterizers draw glyph edges differently. After `bun run fidelity`, `bun scripts/fidelity/rasterizer-control.ts <fixture>` draws the reference PDF as canvas text with pdf.js in the harness Chromium. It prints three counts: the editor page against the pdf.js raster, the pdf.js raster against Poppler, and the editor page against Poppler. The control ran with Poppler 26.10.0, pdf.js 5.4.624, Chromium 158.0.8127.18, and Carlito 1.104 (`@docx-editor.dev/fonts` 2.35.0). The CI runner has no measurement of the control. The percent goes with the third count. The counts are 3, 9495, and 9499 for `number-formats` (0.490%), and 56, 5410, and 5420 for `colors-fonts` (0.280%). They are 0, 746, and 746 for `basic-values`. For `text-layout`, they are 203, 4176, and 4389 (0.226%). For `cell-styles`, they are 388, 1667, and 2055 (0.106%). On `text-layout` and `cell-styles`, the control does not explain every pixel of the editor page. It cannot separate an editor difference from the pdf.js drawing of fills and borders. Their cause is not known. PPTX Editor's harness draws both PDFs with pdf.js, so one rasterizer draws both sides. This harness keeps Poppler for the reference raster, because it measured every pixel limit and known gap on Poppler rasters. A pdf.js reference raster needs each of those values measured again.
- **Line scores of clipped text.** The fidelity harness (`scripts/fidelity/`) reads the text lines of the editor's page from a PDF. Chromium prints that PDF of the painted canvas. The canvas paints for that print at a device pixel ratio of 1, and for the pixel score screenshot at 3. Both paints draw from the same layout in points.

  That PDF leaves out each glyph that a cell clip hides entirely, and the reference PDFs keep such glyphs as text. So a painted line that a clip cuts matches the reference line that starts or ends with its text. The match uses the clip rectangles of both PDFs (`pdf-clips.ts`). The line scores do not check the hidden glyphs. The pixel score covers their area of the page, as a share of all pixels.

  Each rule uses `clipEdgePt`, 0.5 points, as its tolerance. This threshold is apart from the line position threshold. A painted line matches a cut reference line when all of these hold:

  - The reference text runs past the reference clip on the cut side by more than the threshold.
  - The painted clip on that side is within the threshold of the reference clip.
  - The painted line reaches the painted clip edge within the threshold.

  Only the cut side is compared. The clip of an end is the clip of the run that draws the last glyph there. A run that starts a line of the next cell is not part of the line, also where it overlaps it. Neither is a run inside an item of the next cell, under the clip of the run that starts that item. When runs with different clips start that item, the end is unknown.

  Paint draws no glyph for a space. So the clip edge can lie in a space of the reference text, and the painted line can end at the glyph before that space. Such a line is cut when all of these hold:

  - The painted line ends within the threshold of the advance end of that reference word.
  - The clip edge lies past that end, within the threshold.
  - The clip edge lies before the advance start of the next reference word, within the threshold.

  The reader takes the advance extent of each reference word from the white space glyphs of its text run, or from the items of the line. It does not read side bearings, so the ink of a glyph can lie past its advance.

  The gate fails in these cases:

  - The reference clip cuts a line, and the painted line is not cut at the same edge. This rule also holds when the texts match in full.
  - The reference clip holds an end of a line whole, and the painted line runs past the painted clip there by more than the threshold.
  - The painted clip hides whole glyphs at such an end, or its edge lies in a space there. The painted line then holds only the start or the end of the reference text.
  - The painted clip is unknown at such an end. No painted run lies there, or its clip is not one rectangle that holds the baseline. Or runs with different clips start an item of the next cell there.

  The rules apply to each end of a line of upright text where the reference clip is known. A known clip is a run with no clip, or one rectangle that holds the baseline. The reference clip of an end is also unknown when runs with different clips start an item of another line. That item must reach the end item of the line. An end of a matched line with an unknown reference clip fails the gate, because no rule checks it.

  Each line holds the items of one clip. The reference PDF clips only text that overflows its cell, and the other text of a row shares the clip of the print area. So the overflow of a cell and the text of the next cell stay two lines. The texts of two cells that fit can form one line. The painted page clips the text of each cell, so it shows two lines there. Each inner end of such a painted line keeps the rules of a line end, against the reference clip of the characters that it holds. The rules need each reference clip as one axis-aligned rectangle. A reference PDF without it, or with another clip path, gives an unknown reference clip. A cut line then stays missing. A painted clip that is not one rectangle fails the gate as an uncut or an extra cut line.

  The clip reader keeps the text state through each save and restore, and counts the word spacing of each space glyph. A form XObject paints as a save and restore, under its form matrix and clipped to its bounding box. The clip of text with a text rise is unknown. So is the clip of text after a render mode that adds text to the clip path. In the reference PDF, such a clip is unknown too.

  These cases have limits:

  - A text run starts at its first glyph that is not white space, and ends at its last one, without the spacing after it. No reference PDF measures a text run that starts or ends with a space glyph.
  - No reference PDF measures a clip edge inside a space.
  - The reader takes glyph widths in thousandths of the font size. So a Type 3 font with another font matrix gives wrong run ends.
  - When the texts match in full, a line that a clip cuts on both sides compares both edges as cuts. Centered text wider than its cell is an example.
  - When the painted page holds only part of a line that a clip cuts on both sides, the line stays missing. The report names it with that cause.
  - The rules compare only the left and right clip edges. A clip that cuts the top or the bottom of a line and still holds its baseline passes. No reference PDF measures a top or bottom clip edge.
  - The line scores check a line of two or more visible characters, or of one digit. A painted line of one character other than a digit matches only as a clipped line. Its clip edge must be within the threshold of the reference clip, and the line must reach that edge. Its character must start or end the reference text on the cut side. No reference PDF measures a painted line that keeps one character other than a digit. No clip rule checks a cell of one character other than a digit: a clip that cuts part of that character passes. Such a line has no line score. `grid-structure` and `text-layout` hold such cells, so their position and clips are unchecked. Stacked text is upright, and each of its lines holds one character, so this limit covers it. The run and the report state the gap with the count of such reference lines.
  - A cut line matches only when the painted line holds the reference glyphs that the clip leaves. The glyph advances of the reference PDF decide which glyphs those are, within the threshold. Reference glyphs can fail to account for the text of the line, such as a ligature or a glyph without Unicode. Then the line matches by its text. Its cut end then fails the gate as a skipped check. No reference PDF measures such glyphs.
  - A cut line matches by its visible characters, without white space, on both sides, as the line keys of PPTX Editor do. So a painted line that loses, adds, or moves a space still matches, such as `Keptconte` or `Kep tconten` for `Kept content`. No reference PDF measures a cut line that differs only in white space.
  - Lines pair in this order. First, lines of the same text on one row, within `maxBaselineDeltaPt`, pair. Then the bullet form on the row pairs, and then the joins. Then the clipped pass and the extra-cut pass run. Then lines of the same text that are left pair on any row. Last, a clipped line that is left pairs with a cut of it on any row. Each step except the clipped pass and the extra-cut pass takes its pairs nearest pair first. So its pairs do not depend on the order of the lines on a page. The clipped pass and the extra-cut pass take the reference lines in page order. The pairing has no limit on the nearer edge, so repeated text on one row can still pair across cells. A wrong pair of clipped text fails the gate as an uncut or an extra cut line. No reference PDF measures repeated text that pairs across cells.
  - A line scores the nearer of its start and end distances, as in PPTX Editor. So a line passes the line scores when only one of its ends moves, from a wrong width or from a word that moves inside the line. No check bounds the width of a line. The pixel score counts the moved glyphs only as a share of the whole page, so a sparse page can pass with them. The run prints this limit as a coverage gap.
  - The line scores leave out rotated, mirrored, and vertical text items. So no clip rule checks a cell of rotated, mirrored, or vertical text. When a reference PDF holds such items, the run and the report state the gap with their count.

  The known gap list names each line that a clip shortens in each fixture, by text, baseline, and the clip edge of the reference PDF. It names a line once for each time a clip cuts it. Another clipped line, or a named line cut more often, fails the gate.

- **Join gap limit.** The line scores of the fidelity harness can join several lines of one page. Each of them lies within `maxBaselineDeltaPt` of a line of the other page. The joined lines then hold one line of the other page (`joinable` in `scripts/fidelity/compare.ts`). Where the items of the whole line split at the pieces, the gap of the pieces is at most 1 em plus 1 point. That point is `joinGapPt` at each end. Elsewhere it is at most 1 em plus `joinGapPt`. A piece that is narrower than its reference characters, aligned at its far end, widens the gap. Such a piece can go past this limit, while the same geometry as one line passes. Then the reference line is missing and the pieces are extra, so the run fails on line breaks and extra text. The same holds for a join piece that moved along the row past the gap limit. It also holds for a join piece that moved off the row past `maxBaselineDeltaPt`. The same move of one line fails on line position or on the baseline. For a moved piece, the report names another cause, but the run fails either way. No reference PDF measures a gap of the pieces near the limit. No reference PDF measures a join piece that moved along the row past the gap limit, or a join piece that moved off the row. On the painted page, the joins of the measured fixtures have gaps of 5.3 to 8.5 points.
- **Reference items across cells.** The PDF reader can merge the text of two adjacent cells into one item of the reference PDF. This happens when the cells share a clip and their gap is about 0.1 to 0.6 em. The painted page draws each cell under its own clip, as two lines. The join then names the inner ends as `painted split inside a reference item`, and the run fails, also for a correct paint. The remedy of the gate names this cause next to the paint. No reference PDF measures a reference item that holds the text of two cells.
- **Conditional formatting rules.** The engine shows a rule of type `cellIs` (`x:cfRule`, `ST_CfType`, ECMA-376 Part 1, 18.3.1.10) whose operands are literals: a number, a quoted string, `TRUE`, or `FALSE`. It does not show other rule types, operands that need a formula, or rules in the extension content (`x:extLst`) of a worksheet. It also does not show rules past the limits of a sheet, rules whose `@sqref` holds more than 512 ranges or 16,384 characters, rules with an operand longer than 8,192 characters, or rules that do not agree with the schema (design D2 of the change `workbook-conditional-formatting`). It also does not show a rule whose `@sqref` has a whole-column range (`A:A`), a whole-row range (`1:1`), a `$` mark, or a lowercase column letter, which the schema allows. For one cell, it walks at most the first 64 shown rules and checks at most the first 1,024 rule ranges of the row. One layout stops checking when it has used 4,000,000 rule-range checks; past that, the other cells keep their cell formats, and the editor shows the notice. The plain text of a copy and the announcement of the active cell take the number format of a true rule. After a budget cut, both use the cell format. A copy has its own 4,000,000 checks, and it charges each row once in full, so its result depends only on the range. A copy or a cut that uses them up is refused with `copy-conditional-limit`. A rule that it does not show never paints and never stops a lower rule. When a sheet has such a rule, more shown rules or ranges than the caps of one cell or one row take, or a layout past its budget, the editor shows a notice for the sheet. The format controls read and set the cell format. When a true rule shows a different state of a format control at the active cell, the tooltip of that control says so. A shown rule reads the stored value of its cell, also a cached formula result that is out of date, from an edit or from the file. The rules take effect in ascending priority, and `stopIfTrue` ends the walk, as ECMA-376 Part 1, 18.3.1.10, states. Each property takes the first value that a true rule sets. The differential format (`x:dxf`, ECMA-376 Part 1, 18.8.14) sets the font and the number format. Its fill paints its `x:bgColor`, under `solid` or no `patternType`. Without `x:bgColor`, the cell keeps its own fill, and a cell with no fill paints white. A gradient fill, another pattern type, and borders keep the format of the cell. A differential font size does not change the row height, so large text can clip. A rich text run that sets a font property keeps it over the differential format. The reference PDF of `preserved-parts` measures one rule that sets bold. The reference PDF of `conditional-rules` measures the eight comparison operators of `ST_ConditionalFormattingOperator` (ECMA-376 Part 1, 18.18.15) that a `cellIs` rule takes; number and string operands; text, boolean, error, and empty values, also cells without an `x:c` element; the fill, theme colors, font color, italic, the presence of strike and underline, and number format of a differential format; two true rules that set different properties; and `stopIfTrue`. On that reference PDF, layout draws the underline of B19 0.5 point higher and 1 point shorter, and the strike of B6 about 0.8 point higher, and 1.04 points thick against 1 point; the pixel score holds these offsets, and no test pins them. These cases follow the code without a measurement: a formula cell with a cached value, and a formula cell without one, which does not take part; rules with equal `@priority`, which walk in document order; boolean operands, and the order of numbers before booleans; the order of strings by UTF-16 code unit after lowercase; number equality without rounding; a value equal to a bound of `between` or `notBetween`; a stored value that cannot be read, such as a bad number, which compares as an empty value; date values, and an empty value under a boolean operand, which make a rule false; the font family and the font size of a differential format, and text that clips in its row; `patternType="none"`, another pattern type, and a gradient fill in a differential format; differential borders; a `solid` fill with only `x:fgColor` over a cell with no fill; an `x:patternFill` with no color, an `x:bgColor` that does not resolve, and a `solid` fill with both `x:fgColor` and `x:bgColor`; two shown true rules that set the same property, and a differential font that turns a property off; a rule that is not shown with `stopIfTrue`, or that is true above a shown rule that sets the same property; a true rule without `@dxfId`, or with a `@dxfId` that no `x:dxf` has, with `stopIfTrue`; a fill with only `x:fgColor` before a true rule with `x:bgColor` over one cell; an empty merged range under a rule; a rich text run under a true rule; a differential fill over a cell with a pattern fill or a gradient fill; a differential font over a cell with its own font properties; a differential number format over a cell with its own number format; a differential color that is `auto` or a system color (`indexed` 64 or 65); underline styles other than `single` in a differential font; a differential `x:vertAlign`; and a rule that covers a cell of a merged range other than its top-left cell.
- **Cut references.** A paste of cut cells moves their values, formulas, and cell formats, and clears the cut cells in the same undo step. A formula elsewhere that refers to a cut cell keeps the old address, so after the paste it refers to the cleared cell. A cut formula does not move its own references: it keeps the cells that it refers to. On another sheet, each reference without a sheet name gets the name of the sheet of the cut. So does each name that the sheet of the cut scopes. The `clipboard-edit` fixture saves a cut and paste with this result. A paste that gets only plain text never moves cut cells. It ends a pending cut, and the live region says that the cells stay. Such a paste writes the shown text, so a formula becomes its shown value, and a number takes its rounded shown text.
- **Cut cell attachments.** Hyperlinks, comments, data validation, and conditional formatting stay with the source cells. A copy or a cut does not take them. A paste writes only values, formulas, and cell formats. The plain text of a copy shows the number format of a true conditional formatting rule, but a paste never carries the rule.
- **Pasted rich text and errors.** A paste in the workbook writes the text of a rich text cell as plain text. So its runs take the font of the cell format. It writes a stored error value, such as `#N/A`, as text. A cell value input holds no runs and no error value.
- **Quoted pasted text.** A paste of plain text splits rows at each line break and cells at each tab, and quotes have no meaning. Other programs write a cell with more than one line as a quoted value with a line break. Such a value splits into rows at the break, and its quotes stay in the text.
- **Copied line breaks.** A copy writes the shown text of each cell to the plain text of the clipboard. A tab goes between cells and a line break between rows. A tab or a line break inside the text of a cell becomes a space. So the plain text keeps one row for each row of the copy. A paste of that copy in the editor uses its own content and keeps the breaks.
- **Clipboard keys in a shadow root.** In WebKit, the copy, cut, and paste keys do nothing in a grid that a host page places in a shadow root.
- **Sheet titles in the document properties.** A sheet add, rename, delete, or move leaves `TitlesOfParts` and `HeadingPairs` in `docProps/app.xml` as they were. These titles describe the sheets for file browsers and search; the workbook reads its sheets from the workbook part. The `sheet-ops` and `sheet-add` fixtures save sheet edits with this result.
- **Legacy drawing anchors.** A resize keeps the cells of legacy drawing anchors. A legacy drawing (VML), such as the box of a comment, gives its anchor as cells in `x:ClientData/x:Anchor`, and the editor does not read it. So after a resize, such a box keeps its cells and can change its size or position. A drawing or a control that keeps its size or position refuses the resize instead.
- **Wrapped formula values.** A cell can keep its formula and its cached value in a branch of an `mc:AlternateContent` child, with no direct `x:f`. The engine does not check the `@Requires` namespaces of an `mc:Choice` in a cell. So it reads `mc:Fallback` first, as ECMA-376 Part 3 states for such a consumer, and then each `mc:Choice` in document order. The formula is the first `x:f` in that order. When the cell has no direct `x:v`, it shows the `x:v` of the branch of that formula. If that branch has none, it shows the `x:v` of the first branch that has an `x:v` and no `x:f`. A value next to another formula is the result of that formula, so it is never shown with the formula of another branch. Unit tests read these values after an edit, a save, and a reopen. The fixture `wrapped-formula` measures one case: an `mc:Choice` that requires a namespace that no consumer understands, so the reference shows the value of `mc:Fallback`. No reference PDF measures an `mc:Choice` whose namespace the consumer understands, a cell with no `mc:Fallback`, or a value from a branch with no `x:f`. None measures an `mc:Fallback` with a value and no `x:f`, beside an `mc:Choice` with a formula. The engine then shows the formula and the value of that `mc:Choice`. In those cases, the value that this order picks can differ from the reference.
- **Decimal padding beside a literal.** In the zero section of a code with three or more sections, a run of `?` after a quoted literal or a dash pads it. A decimal step adds or removes one `?` there. Only a section with a fill and a dash gets its `?` back, after the last dash before the run: `"-"`, `\-`, or `-`. Another literal can follow the run, as in `"-"??\ "€"`. An empty run gets its `?` back only when the sections before it have no places, as after a decrease to no places. Beside another literal, or with no fill, a decrease to no places removes the last `?`, and an increase does not add it back. So `0.00;-0.00;"x"??` goes down to `0;-0;"x"` and up again to `0.00;-0.00;"x"`.
- **Decimal places split by a literal.** A decimal step adds or removes the last decimal placeholder of a section. A literal or a second point can split the decimal places, as in `0.00" "0`, `0.00%0`, or `0.0.0`. The step can then move a place to the other side of the literal. So `0.00" "0` goes down to `0.00" "` and up again to `0.000" "`.

## Coverage gaps

The fidelity harness has no measurement for these cases, so a row of the support matrix that cites a fidelity fixture does not cover them. `bun run fidelity` prints each one, and a test (`scripts/fidelity/harness.test.ts`) keeps this list equal to `COVERAGE_GAPS` in `scripts/fidelity/report.ts`. A run also prints, with their count, the lines of one character other than a digit and the rotated, mirrored, and vertical text items, when its fixtures hold them. Approximation "Line scores of clipped text" names both.

- The harness renders the print profile (`PRINT_PROFILE`) only. The screen profile (`SCREEN_PROFILE`), the default of the editor, has no fidelity measurement.
- The harness does not check that each glyph draws in the face and size of its cell.
- The line scores take the nearer end of each line, so no check bounds the width of a line or the place of a word inside it. The pixel score counts such glyphs only as a share of the whole page.
- On a fixture with many glyphs, the rasterizer difference takes most of the page limit. So the pixel score of such a fixture cannot see a paint change that is smaller than the rest of its limit. Design D8 (`openspec/changes/typed-ooxml-workbook-editor/design.md`) gives the measured `number-formats` scores and margins on each recorded toolchain. `bun scripts/fidelity/rasterizer-control.ts <fixture>` compares the editor page with a pdf.js raster in the same Chromium, but no gate runs it.
- No fixture names a family that the editor draws with a substitute face, such as Calibri. The fixtures name the substitute faces themselves, so no fidelity check measures the substitution. A row that cites a fidelity fixture shows the substitute faces only.
