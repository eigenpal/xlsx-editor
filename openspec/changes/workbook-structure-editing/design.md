## Context

The first change `typed-ooxml-workbook-editor` makes `WorkbookDocumentStore.transact` over typed ops the only write path (D2). It refuses an edit that it cannot make exactly, and names the subject (D4). Row and column insertion and deletion move references through the formula tokenizer (`store/formula/`) and refuse content that they cannot move (`store/structure/blockers.ts`).

DOCX Editor and PPTX Editor solve the same problems for their formats. This change follows them, at DOCX Editor `origin/main` `f3116761` and PPTX Editor `origin/main` `79a5d22d`:

- Clipboard events: DOCX Editor `packages/core/src/editor/surface-input.ts:466-508`. The engine never reads the clipboard: a paste takes its text as an argument (`clipboard-write.ts:7-9`). A paste is one commit and one undo unit (`surface-clipboard-ops.ts:353-411`). A cut reads before it deletes (`docx-editor-exec.ts:549-580`).
- Private clipboard format: PPTX Editor `packages/core/src/editor/clipboard.ts:42`, which also accepts plain text equal to its last copy (`:69-82`). This change does not: see D2.
- Drag resize: DOCX Editor `packages/core/src/editor/surface-table-interaction.ts:413-452` (6 px handles), `:574` (pointer capture), `:869-877` (pointer cancel and Escape cancel), `:633-640` (an end equal to the start commits nothing), and one op on pointer up (`table-command-plan.ts:665-674`).
- Slide operations: PPTX Editor `packages/core/src/automation/commands/slide-commands.ts` (`addSlide` :200, `deleteSlide` :323 refuses the last slide, `moveSlide` :352 emits nothing for a move to the same place), context menu `packages/react/src/RailContextMenu.tsx`, inline rename `packages/react/src/RailSections.tsx:340-374`.

## Goals and non-goals

Goals: the three features of the proposal, each through typed ops, with undo, refusals, and a save check. Non-goals: the list in the proposal.

## Decisions

### D1. Sheet ops

- `addSheet {name, index}` adds a worksheet part `/xl/worksheets/sheetN.xml` with the smallest free `N`, a workbook relationship with a new `Id`, an `x:sheet` with `sheetId` one more than the largest, and a content type override. The new part has an empty `x:sheetData`.
- `renameSheet {sheet, name}` changes `x:sheet/@name` and rewrites the sheet prefix of each reference to the sheet in every formula (`x:f`) and defined name (`x:definedName`) of the workbook. Internal hyperlink locations (`x:hyperlink/@location`) are rewritten in the same way, and so is a hyperlink relationship target of a worksheet that is a fragment (`#Data!A1`): the text after the `#` is a location. A target with a `%` escape that can name the sheet refuses the op (`structure-blocked`), because the editor does not decode it. A fragment holds only the characters of RFC 3986, 3.5. So when the new text holds another character, such as the space of `'Q 1'!A1` or a character outside ASCII, each hyperlink that uses the relationship takes the text as its `@location`, and the relationship goes, as for a delete. A new prefix is quoted unless the name holds only ASCII letters and underscores and does not start like a boolean or an R1C1 reference, so a name with a digit or a dot (`A1.B`, `R1C1x`) never reads as a reference.
- `deleteSheet {sheet}` removes the part, its relationship, its override, and its `.rels` part. Each reference to the sheet becomes `#REF!` with its address: `Sheet1!B2` and `Sheet1!A1:B2` become `#REF!`, in formulas, defined names, and internal hyperlink locations. A fragment cannot hold `#` (RFC 3986, 3.5), so a hyperlink whose relationship target names the sheet takes `#REF!` as its `@location`, and the relationship goes; a hyperlink with both `@r:id` and `@location` refuses the delete (`structure-blocked`). Measured with the save check: a formula or a defined name that holds `#REF!B2` does not open, and a measured sheet delete writes `#REF!`. So no address stays after `#REF!`, and a later row or column edit has nothing to move. A range operand that the `:` operator joins (`Sheet1!A1:Sheet1!B2`) becomes one `#REF!`. A defined name with `@localSheetId` of the sheet is removed. The other `@localSheetId` values move down. When the workbook has formulas, a delete sets `x:calcPr/@fullCalcOnLoad` and drops the calculation chain, as a formula edit does.
- A formula (`x:f`) or a defined name can name a sheet that does not exist yet, and its cached result then holds an error. An add or a rename that gives a sheet that name makes the formula read the sheet. So when a cell formula or a defined name already names the new name, the op marks the cached results stale as a value edit does: the saved workbook asks for a full calculation on load (`x:calcPr/@fullCalcOnLoad`).
- Some functions read sheet names or positions without a sheet prefix: `INDIRECT`, `CELL`, `INFO`, `SHEET`, `SHEETS`, and `FORMULATEXT` (stored as `_xlfn.SHEET`, `_xlfn.SHEETS`, and `_xlfn.FORMULATEXT`). A rename rewrites the formula text that `FORMULATEXT` returns. A macro function `GET.*`, which only a defined name can call, can return sheet names or positions: `GET.WORKBOOK` returns the sheet names, and `GET.DOCUMENT` and `GET.CELL` read sheet facts. So the scan counts every call whose name starts with `GET.`. An applied add, rename, or move changes no reference, but it can change their results. So when a cell formula or a defined name calls one of them, the op marks the cached results stale in the same way. The tokenizer reads each formula text that holds the name of one of the functions. A text that it cannot read counts as a call. A delete always marks them stale.
- The row and column edits of the first change (design D4 of `typed-ooxml-workbook-editor`) take three rules of this change. A row or column edit of a sheet whose name a file gives to another sheet too, in any case, is refused with `sheet-name-ambiguous`, with the other sheet as the subject. A stored sheet name longer than 31 characters refuses it with `sheet-name-too-long`, with that name as the subject. A hyperlink relationship target that is a fragment (`#Data!A5`) moves with the cells that it names, as `x:hyperlink/@location` does.
- The sheet protection of the first change (`x:sheetProtection`) takes six rules of this change: the fields `allowFormatColumns` and `allowFormatRows` with the lock rule `size` (D3), the paste rule of a new cell format, the protection-change rule, the clear rule, and the cut rule (D2), and the workbook rule below. The proposal lists them under Modified Capabilities.
- `moveSheet {sheet, index}` moves the `x:sheet` element. `@localSheetId` and `x:workbookView/@activeTab` follow the moved sheets. An absent `@activeTab` reads as its schema default, 0 (`CT_BookView`), and a workbook with no `x:bookViews` reads as one view with the first sheet active. A sheet op writes `@activeTab`, and adds `x:bookViews` only when the active tab changes. `@firstSheet` is the first tab that the tab strip shows: a scroll position, not a sheet. A sheet op never writes an absent `@firstSheet`, and a present one keeps its index. After a delete or a move, the op clamps it to the last position and to `@activeTab`. A move to the same place emits no op.
- A sheet name has 1 to 31 characters, counted in UTF-16 code units (a character outside the Basic Multilingual Plane counts as two), none of `[ ] : * ? / \`, no control character (U+0000 to U+001F, tab and line breaks included), no other character that XML 1.0 cannot hold (a workbook cannot store it), no `_xHHHH_` sequence, no apostrophe at the start or the end, and no case-insensitive match with another sheet name. These are this editor's rules: the schema types `x:sheet/@name` as `ST_Xstring` (`CT_Sheet` in `sml.xsd`; ECMA-376 Part 1, 22.9.2.19) with no length limit, and the rules keep a name readable as a formula prefix. In `ST_Xstring`, `_xHHHH_` is the escape of one character. The editor shows and matches a stored sheet name as written, without decoding, so it refuses to write a name with such a sequence, and the stored name and the shown name stay the same. A name that breaks a rule is refused with `sheet-name-invalid` or `sheet-name-taken`. Names compare without case through a fold that keeps the length: a code point becomes its uppercase only when that uppercase is one code point, so `Maße` and `MASSE` are two names. A new name is also taken when it equals another sheet name after both take their canonical composition (NFC) and the fold, so `Café` with U+00E9 and `Café` with U+0301, or `k` and the Kelvin sign U+212A, cannot both come from the editor. The lookup of a stored name does not use NFC. A file can still hold two sheets whose names match without case (`Data` and `DATA`). An op finds a sheet by its exact name first, and a name that matches more than one sheet finds none (`unknown-sheet`). A delete and a row or column edit of such a sheet are refused with `sheet-name-ambiguous`, with the other sheet as the subject, because a prefix such as `DATA!A1` can name either sheet. A rename of such a sheet is refused the same way when a formula, a defined name, a hyperlink location, or a hyperlink relationship target names one of the two; a rename that changes no reference is applied, so it ends the ambiguity. The sheet tabs name a sheet by its position: a command whose sheet name finds another sheet, or none, is refused with `sheet-name-ambiguous`, with the other sheet as the subject, and a position with no sheet with `unknown-sheet`.
- Each op is refused, with the subject named, when the edit cannot keep the workbook valid:
  - A rename and a delete keep the whole part blocker of D4 of the first change: any chart, pivot table, or sheet that is not a worksheet, such as a chartsheet, in the workbook refuses them, and so does a workbook or package relationship outside the allowlist. Content that names the sheet and that the op does not rewrite also refuses them: tables, query tables, and the other mention blockers of D4.
  - A move refuses a 3-D reference (`Sheet1:Sheet3!A1`) in a formula or a defined name only when the move changes the set of sheets between its ends, or which end comes first in tab order, because the store does not rewrite sheet ranges. A swap of the ends (`Jan:Feb!A1` after `Feb` moves before `Jan`) spans the same sheets, but no evidence shows that a workbook with the swapped text opens, so it is refused. A sheet range in content that the op does not read (the mention blockers) refuses any move. Both refusals have the code `sheet-range-blocked`. A move changes no reference text, so charts and pivot tables never refuse it, and the message of `sheet-range-blocked` names no chart.
  - The mention blockers also scan the drawing, legacy drawing (VML), and control property parts that any worksheet relates to, and the relationship part of each: a shape `textlink`, a control `fmlaLink` or `fmlaRange`, a VML `x:FmlaLink`, and an internal hyperlink target (`#Sheet1!A1`) can name the sheet. An unquoted sheet range start (`A:Z!`) needs its `!`, so a whole column such as `A:A` is not a mention of a sheet named `A`. The scan reads each text once. It looks for the spellings of the edited sheet. At each `:`, it walks a trie of the sheet range spellings of every sheet, back and forward. So its cost grows with the text and not with the number of sheets times the text. A walk reads at most the longest spelling. A file can store a sheet name longer than 31 characters. Then a move, a delete, and a row or column edit refuse the workbook with `sheet-name-too-long` before the scan, with the full stored name of that sheet as the subject. A rename does not scan sheet ranges, so it can shorten the name.
  - A rename is refused with `structure-blocked` when a local sheet range names the sheet and its start or end reads as a cell. The tokenizer reads `SUM(A1:S!B2)` as a range from `A1` to `S!B2`, so a rewrite of the prefix can change its meaning. The formula keeps its text.
  - A sheet name or a sheet range after an external workbook index (`[1]Jan!A1`, `[1]Jan:Mar!A1`) names sheets of another workbook. The tokenizer reads the index and the names as one prefix, so a rename, a delete, a move, and a row or column edit of a local sheet with the same name keep the text, and a copy does not depend on it.
  - A delete also refuses a 3-D reference whose start or end is the sheet (`sheet-range-blocked`). A sheet between the two ends leaves the range, and the reference text stays the same. A delete also refuses a sheet part with relationships other than hyperlinks and printer settings, a custom workbook view whose `@activeSheetId` is the sheet's `sheetId`, and the last visible sheet (`last-sheet`). Printer settings that no other part relates to go with the sheet, with their override.
- A refusal of a blocked op has the code `structure-blocked`. Its message is general, because the code serves row, column, and sheet edits: the subject refers to content that the edit changes, and the editor cannot change that reference. Its sentence on charts names only the edits that a chart refuses: an insert or delete of rows or columns, and a sheet rename or delete.
- The inverse of each op is one `restoreParts` op of the parts that it changed. The calculation chain drop of the first change is outside the undo history, so an undo can put back a workbook relationship part or a content type part that names a dropped chain. The same transaction drops that relationship and override. The store refuses a transaction that leaves a new workbook relationship or content type override to a missing part.
- The workbook protection (`x:workbookProtection`, ECMA-376 Part 1, 18.2.29) locks the sheet list when `@lockStructure` is true. Its schema default is false (`CT_WorkbookProtection` in `sml.xsd`). Then each sheet op is refused with `locked` and the lock rule `workbook`, before it applies. The snapshot holds `workbookProtection` (`allowStructure`), and the sheet tabs disable the add button and the Rename, Delete, Move left, and Move right rows with the reason `workbookLocked`. The store does not enforce `@lockWindows` or `@lockRevision`, and it keeps the password hashes as the file holds them.
- `docProps/app.xml` is not modeled. Its sheet titles (`TitlesOfParts`) and the sheet count in `HeadingPairs` go out of date after a sheet op (approximation `sheet-titles`). The `sheet-ops` fixture holds these titles, and its edited copy, with three stale titles, opens in the save check with no repair prompt. The `sheet-add` fixture adds a third sheet to a workbook whose titles list two, and its edited copy also opens with no repair prompt.

### D2. Clipboard

- The engine never reads the clipboard on its own. The grid surface of the editor listens to the `copy`, `cut`, and `paste` events (`clipboard-events.ts`): it writes the copy to the event data, and it passes the text and the private marker of a paste event to the clipboard module, as DOCX Editor does. No adapter wires the clipboard.
- A copy keeps a snapshot of the range in the editor: for each cell, its input (a value or a formula) and its cell format index. A copy writes `text/plain` (tab-separated values of the shown text) and the private type `application/x-xlsx-editor`, which holds only a token of the snapshot. The shown text of any value that starts with `=`, `+`, `-`, `@`, tab, or CR gets an apostrophe in `text/plain`, as the AGENTS.md rule on text exports states, except the shown text of a number or a date that is one signed number with a digit after its sign and an optional currency symbol, such as `-1,234.50`, `-$1,234.50`, or `-1.2E+03` (`exportCellText`); `-1+2` and `-$A$1` get the apostrophe. A tab or a line break inside the shown text becomes a space, so `text/plain` keeps one row for each row of the copy (approximation `copied-line-breaks`). A date whose shown text does not read back as typed input to the same day, such as `2-Jan` or a two-digit year outside 1930 to 2029, gives its edit text, such as `2035-06-01` (`copiedDateText`), so a plain-text paste stores the same date.
- A paste routes in this order: the private token of the last copy, then `text/plain`, then refuse `paste-html` when only `text/html` exists. An empty clipboard changes nothing. The token goes to the internal lane only for the store of the copy: the editor forgets the copy when it opens another workbook or is destroyed, so a cut never clears cells of another workbook.
- Plain text equal to the last copy, with no token, takes the plain lane. PPTX Editor pastes such text as its last copy (`clipboard.ts:69-82`), because a slide copy holds content that plain text cannot. Here the plain text holds every value as shown, and text from another program can match a copy by chance; the plain lane writes what the text says and never clears cut cells that the user did not paste back.
- An internal paste writes the snapshot at the active cell. A formula moves by the offset between the source and the target (`moveFormula`), and a reference that leaves the grid refuses the paste with `paste-reference-outside`. The cell format index is set with the op `setCellFormatIndex`. A cut is a move: its formulas keep the cells they refer to, and the paste clears the source in the same transaction. On another sheet, each reference of a cut without a sheet name gets the source sheet name (`qualifyFormula`). On another sheet, a copy and a cut apply one name rule, after the copy moves its references by the offset: a name that the source sheet scopes (`@localSheetId`) gets the source sheet name, so it does not bind to a name of the target sheet (`Src!name`; a sheet name that is not a plain word is quoted, as in `'Src 1'!name`), and a name with no sheet prefix that the target sheet scopes and the source sheet does not refuses the paste with `paste-name-scope`, because no prefix names the workbook scope. A cut depends on its source sheet. A copy with a name that the source sheet scopes depends on the source sheet only for a paste on another sheet, so a rename or a delete of that sheet refuses a later paste there with `copy-expired`. A paste on the source sheet keeps the binding, also after a rename: the source sheet is the one whose `x:sheet` element has the node id that it had at the copy. A function name counts as a name, because a defined name can hold a function. A function name that the source sheet scopes refuses the paste on another sheet with `paste-name-scope`, whose text says to paste on the source sheet. The evidence is the store: it refuses the text `S1!myFn(1)`, because the tokenizer reads the name `S1!myFn` and then a group, and the grammar check reports `missing-operator`. A prefix `[0]` names this workbook, so its sheets count as the sheets of a local prefix. An unquoted sheet range whose start or end reads as a cell reference refuses the paste with `paste-unreadable-formula`, because a moved or qualified text can change its meaning. The tokenizer reads `A1:S!B2` as a range from `A1` to `S!B2`, and the check of typed input refuses it, so its paste is refused too, also in a cut on the same sheet. References to the cut cells do not move. After one paste of a cut, the next paste is a copy. One rule decides whether a paste can use the snapshot: it uses it only while everything that the snapshot depends on is unchanged. That is the store of the copy; for a cut, its source cells, as the store revision of the cut; every sheet that a copied formula prefix names, read by the tokenizer, and the source sheet of a cut or of a copied formula with a name that the source sheet scopes, each as the `x:sheet` element that its name finds, by identity (the tree is immutable: a delete and a new sheet with the same name give a new element, though the new sheet can reuse the part name and `sheetId`; a move keeps the element, and an undo restores the same element); and the `x:xf` element of every copied cell format index, with its font, fill, border, and number format code, compared by identity or by structure. A sheet that no copied formula names does not count. When the source cells of a cut changed, the paste is refused with `cut-expired`, because a copy in its place would leave the source cells that the user meant to move. When anything else changed, the paste is refused with `copy-expired`. Either way, the same clipboard token stays refused with the same code, and never falls to the plain lane, until a new copy, a new cut, or a reset. An empty source cell copies the format that it shows. A copy has its own refusal codes: `copy-too-large` for more than 16,384 cells, `copy-array-formula` for a range that meets an array or data table range, also without its master cell, and `copy-unreadable-formula` for a formula whose text the copy cannot get: an empty `x:f`, or a shared formula child whose master is missing or whose master text cannot move to the child, and `copy-wrapped-formula` for a cell whose formula is inside `mc:AlternateContent`, which has no text that a paste can move. A copy keeps any other formula as its text, also one that the tokenizer cannot read. Such a formula refuses the paste, when the paste moves it, with `paste-unreadable-formula`, not `unreadable-formula`, whose text is advice for typed formulas. The store checks a written formula as typed input (`readFormulaInput`), so a copied or cut formula that fails that check, such as `1+` or `"open`, also in a cut on the same sheet, refuses the paste with `paste-unreadable-formula` and the source cell as the subject, before any write. A call to a function outside the predefined functions refuses it with `unsupported-function` and the function name. These, `paste-reference-outside`, `paste-name-scope`, `cut-expired`, `copy-expired`, `merged-range`, and `paste-html` are editor codes, because the store does not know merged ranges, HTML, or the clipboard. Rich text pastes as its plain text, and a stored error value pastes as text, because a cell value input holds no runs and no error (approximation `pasted-values`).
- A plain-text paste first counts the line breaks and tabs in one bounded scan, and refuses more than `MAX_FORMAT_NEW_CELLS` with `range-too-large` before any split. It splits rows at CR LF, LF, or CR, and cells at tab. Each cell is read as typed input, as the cell editor reads it. A cell with the General format takes the number format of its typed form, as the change `typed-ooxml-workbook-editor` states (workbook-cell-editing); other cell formats do not change. Quotes have no meaning: a quoted value with a line break, as other programs write a multi-line cell, splits into rows at the break, and its quotes stay in the text (approximation `pasted-quotes`).
- A paste is refused when its target leaves the grid (`grid-full`, with the target range as the subject), covers more than `MAX_FORMAT_NEW_CELLS` cells (`range-too-large`), or meets a merged range (`merged-range`). A copy of a range that meets a merged range is refused in the same way.
- A copy and a cut take values, formulas, and cell formats only. Hyperlinks, comments, data validation, and conditional formatting stay with the source cells (approximation `cut-cell-attachments`).
- A cut changes no cell until the paste, so it announces its range in the live region of the grid (`grid.cut`). A copy announces its range in a short text (`grid.copied`). A dashed outline in the editor overlay marks the source range of a pending copy or cut. A copy with formulas expires with `copy-expired` at an insert or a delete of rows or columns on any sheet, at a rename, a move, or a delete of a sheet that a formula names, and at an undo or a redo of such an edit. A formula with a reference across a span of sheets also expires at an add, a rename, a move, or a delete of any sheet, because the span can then hold other sheets. Escape on the grid of any sheet ends the outline of a pending copy and keeps the copy, so a later paste of its token still writes the copied cells. Escape on the grid of any sheet forgets a pending cut: the source cells stay, and a later paste of its token takes the plain lane. The live region says so, also on another sheet. The next Escape goes on to the grid exit. A plain-text paste also ends a pending cut and announces it (`grid.cutEnded`), so the user knows that the cells did not move.
- A paste is one transaction and one undo step.
- A copy or a cut that succeeds is the next command, so it clears the last refusal (`snapshot().refusal`), as a stored edit does.
- A cell format changes the result of `CELL("format")`, `CELL("color")`, `CELL("parentheses")`, `CELL("prefix")`, `CELL("protect")`, and `GET.CELL`. So when a cell formula or a defined name calls `CELL` or a macro function `GET.*`, `setCellFormatIndex`, a clear of formats, and `applyFormat` of the first change mark the cached results stale, as a value edit does.
- On a protected sheet (`x:sheetProtection/@sheet`, Part 1, 18.3.1.85), a paste writes a cell format index (`setCellFormatIndex`) for each target cell. When `@formatCells` locks formatting, a new format is a format edit and is refused with `locked` and the rule `format`. A format that the cell already shows changes nothing, so a paste in the same format applies. A paste into a locked cell is refused with the rule `cell`: the value ops come before the format ops of a paste. A new format that changes the `@locked` or `@hidden` protection of a cell is refused with the rule `cell`, whatever `@formatCells` states, so a paste or a script cannot unlock a locked cell and then write it. A `locked` refusal of a paste has the command `paste`, so its message names the paste. A cut clears its source at the paste, as Clear all does: a cut whose source the clear would refuse (a locked cell that holds content, or a sheet that locks formatting) is refused at the cut with `locked` and the command `cut`. The paste clears only the source cells that it does not write, because its writes cover the overlap. On a protected sheet, a clear of formats (`clearFormats`) keeps the `@locked` and `@hidden` protection of each cell. A cell gets format 0 with its own protection, a record that the clear appends when no record holds it. So a cut never changes the protection of a source cell, and a move of unlocked cells applies. A refusal at the cut would refuse that move, so the store keeps the protection instead. A copy changes no cell, so it stays available.

### D3. Resize

- `setColumnWidth {sheet, first, last, width}` writes `x:col` elements with `@width` and `@customWidth="1"` over the columns, and splits the `x:col` elements that it crosses. The width is in characters of the maximum digit width (ECMA-376 Part 1, 18.3.1.13), from 0 to 255. The limit of 255 is this editor's limit: the schema states none.
- A column width changes the result of `CELL("width")` and of `GET.CELL`. So when a cell formula or a defined name calls `CELL` or a macro function `GET.*`, `setColumnWidth` marks the cached results stale, as a value edit does. A row height changes the result of `GET.CELL`, which can read it. So when a formula or a defined name calls a macro function `GET.*`, `setRowHeight` marks the cached results stale too. No result of `CELL` depends on a row height, so a call to `CELL` alone does not mark them.
- `setRowHeight {sheet, first, last, height}` writes `x:row/@ht` and `@customHeight="1"`, from 0 to 409 points. The limit of 409 is this editor's limit: the schema states none. A row with no `x:row` gets an empty one, at most 16,384 in one op; more refuses with `too-many-rows`. Rows out of order in `x:sheetData` refuse with `invalid-sheet`. A resized `x:col` drops `@bestFit`, as its width is no longer a best fit.
- The pointer hits a resize band 3 px on each side of the right edge of a column heading or the bottom edge of a row heading. The cursor shows `col-resize` or `row-resize`. A drag shows the new size and commits one op on pointer up. Escape and pointer cancel cancel the drag. A drag that ends at the size it started with commits nothing, also after it moved away and back. The minimum is 0, and the guide line stops at 255 characters or 409 points. A selection of whole columns or rows that holds the dragged one resizes all of them, as one op for each band of adjacent columns or rows in one transaction.
- A double-click on the resize band of a heading edge fits the column or row to its content. The fit is one transaction and one undo step. A selection of whole columns or rows that holds the edge fits each of them. The layout gives the sizes (`fitColumnWidths`, `fitRowHeights`). A column takes the smallest width at which each counted cell shows its text unchanged at each zoom step from 50% and at the current zoom. A row takes the automatic height of layout at zoom 1. A row with a wrapped cell can take more, where another of those zooms needs more than one pixel of that zoom beyond it. `setColumnWidths {sheet, columns: {column, width}[]}` writes the widths in one pass over `x:cols`. It writes `@customWidth="1"` and no `@bestFit`, as `setColumnWidth` does. The text of 18.3.1.13 gives a best fit width that grows as numbers are typed, and a fitted width does not grow. `setFittedRowHeights {sheet, rows: {row, height}[]}` writes `x:row/@ht` without `@customHeight` in one pass over `x:sheetData`. It removes an existing `@customHeight`, because a fitted height is not a height set by hand (18.3.1.73). So a later font change or value edit fits the row again. Both ops follow the protection and stale values of the resize op of their axis. An anchor refuses a width change, a height change, or the loss of a true `@customHeight` (`1` or `true`) that meets it. A column that only gains `@customWidth` at its width is not refused.
- Drawing anchors keep their cells. A two-cell anchor stretches with its cells, and a `xdr:oneCellAnchor` or `xdr:absoluteAnchor` keeps its size. A `xdr:twoCellAnchor` whose `@editAs` is `oneCell` keeps its size in points, and one whose `@editAs` is `absolute` keeps its position and size, so the store refuses a resize that would change them with `resize-anchor`: for `oneCell`, a range that meets the anchor's columns or rows; for `absolute`, also a range before them. `@editAs` is an `xsd:token`, so white space around it does not count. A `xdr:to` marker with offset 0 ends at the start of its cell, so the anchor's span ends at the cell before it. The anchor of an embedded control (`x:controls/x:control/x:controlPr/x:anchor`) or object (`x:oleObjects/x:oleObject/x:objectPr/x:anchor`) is a `CT_ObjectAnchor` (`sml.xsd`): it keeps its size unless `@sizeWithCells` is true, and its position unless `@moveWithCells` is true; both default to false. A kept size refuses a range that meets it, and a kept position a range that meets or comes before its first cell, also inside `mc:AlternateContent`. The subject of `resize-anchor` is the name of the shape (`xdr:cNvPr/@name`) or the control (`x:control/@name`) when the file gives one; the editor shows a generic label otherwise, never a part name. A drawing part that the resize cannot read (kept as bytes, or not a `xdr:wsDr`) can hold such an anchor anywhere, so it refuses every resize of its sheet with `resize-anchor` and no subject. The anchors of a legacy drawing (VML `x:ClientData`) are not read, because comments use them on most sheets: a resize keeps their cells (approximation `legacy-drawing-anchors`).
- On a protected sheet, `@formatColumns` locks column widths and `@formatRows` locks row heights. Each is true by default (`CT_SheetProtection`). A locked size is refused with `locked` and the new lock rule `size`. `SheetProtection` gets `allowFormatColumns` and `allowFormatRows`, and a heading edge whose size is locked shows no resize edge, as in view mode.

### D4. Chrome

- The sheet tabs get an add button, a context menu (right-click, Shift+F10, or the Menu key) with rename, delete, move left, and move right, and inline rename, started by a double-click, F2, or the menu (Enter or blur commits a changed trimmed name, and Escape cancels). A refused blur ends the rename and keeps the old name, as PPTX Editor `RailSections.tsx` `commitName` ends every rename. Difference: a refused Enter keeps the field open with its text, because `commitName` has no refusal to show, and a taken or invalid sheet name is a common case that the user corrects in place. Escape then cancels and clears the reason; it clears only a reason that the rename made. A rename starts only after an open cell edit commits, and a refused commit keeps its editor and its reason. A press on the grid that blurs a refused rename keeps its reason in view after the press selects a cell. A press on the add button, on another tab, or on a toolbar control commits an open rename first, as a blur does, because chrome `mousedown` keeps the focus in the field; a refused one keeps its reason, and that press, with the double-click or the context menu that it starts, adds, chooses, or renames no sheet, opens no menu, and runs no toolbar command. So Save writes the typed name, and Undo undoes the rename that the press wrote. A press on a control that was disabled at the press, such as Undo before any edit, commits the rename and runs no command, because the commit can enable the control; the block lasts for one click, and a key press, the next press, or the task after a release with no click ends it, so it never blocks a later click from the keyboard. The rename names its sheet by the name it started with, and a change of the sheet list ends it with no write. A rename that holds focus when it ends this way gives focus to the grid. The rename field lies over its tab, outside the tab list, which holds only tabs, and follows the tab when the list scrolls, but stays inside the tab list when its tab scrolls out. It is never wider than the room before the add button, so the button stays in reach. It takes a name of any length, and the store refuses a long one with `sheet-name-invalid`, so the user sees the reason and does not lose characters without notice. A click on a tab gives focus to that tab when the tab list had focus, and to the grid otherwise. The arrow keys, Home, and End move between the worksheet tabs and skip a chartsheet tab, which is disabled with `aria-disabled`, so its press keeps the grid's focus; it takes no keyboard focus, no click, no rename, no menu, and no `aria-haspopup`. A press on the empty part of the tab bar keeps the grid's focus. The tab of the shown sheet scrolls into view when the shown sheet or the sheet list changes, so a renamed tab that grows stays in view. The menu is a panel above the tab row, not a portal, because the tab row scrolls and would clip it; it stays inside the bar. A chartsheet tab opens no menu. A press outside, a window blur, a resize, a scroll of the page, and a wheel outside the menu close it (PPTX Editor `listenAway`); a scroll that code makes inside the page, such as the grid or the tab list, keeps it open. On close, focus goes back to the element that had it at the open (PPTX Editor `ContextMenu.tsx` and `listenContextMenuDismiss`). When that element is gone, such as a rename field that the open ended, or was the page, focus goes to the menu's tab for a key open and to the grid for a press. When a tab had focus at a right press on another tab, focus goes to the pressed tab, as a click on a tab gives it. Delete is disabled with the reason `disabledReason.lastSheet` when one visible sheet is left. `sheetCommandState()` is the one source of the enabled state and the reason of the add button and of each menu row, and each row shows the reason of its own state. A sheet that is not a worksheet is a chartsheet, a macro sheet, a dialog sheet, or a sheet whose part is missing. Such a sheet has rename, delete, and both moves disabled with the reason `notWorksheet`. Its text says that the editor cannot show, rename, delete, or move the sheet. The store refuses a rename and a delete of it. Its tab opens no menu, so the tabs move no such sheet. Its tab shows the reason in its title and its description. The editor command `moveSheet` refuses to move it with `structure-blocked`, as a delete does, because the history names only worksheets. The refusal names the sheet, and its `about` kind is `not-worksheet`. View mode, an open edit, and the workbook protection refuse the move first, as they refuse a delete. A worksheet moves past it. A chart, a pivot table, a sheet that is not a worksheet, or a workbook or package relationship outside the allowlist, such as data connections, disables rename and delete of every sheet with the reason `sheetEditBlocked`, because the store refuses them (D1). The snapshot holds that refusal in `sheetEditRefusal`, read once for each revision. While a rename or a sheet edit is disabled, the title of a worksheet tab, the add button, and each menu row is its label and the reason, as `toolbar.disabledTitle` composes them. A worksheet tab takes the reason of its own rename state, and its description holds that reason, so F2 and a double-click that start no rename are explained. A press on the add button while the tab list has focus gives focus to the tab of the new sheet, as a press on a tab does. Move left and move right move a sheet past the next visible tab, so hidden sheets never take a move. Ctrl+Page Up and Ctrl+Page Down keep their meaning.
- Mod+C, Mod+X, and Mod+V work through the browser clipboard events. The cell editor keeps its own text clipboard.
- A refused command reports its code through the existing refusal channel, with a key `editing.refused.<code>`.
- A new sheet name comes from the catalog key `sheetTabs.newSheetName` with a number, the smallest free one.
- In view mode, every command of this change that writes is refused with `view-mode`: the sheet commands, cut, paste, and the resize commands. The add button and the edit rows of the sheet menu are disabled with the reason `viewMode`, no rename starts, and a heading edge starts no resize. A copy changes no cell, so it works in view mode.
